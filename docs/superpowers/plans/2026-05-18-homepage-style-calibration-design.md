# 首页 LLM 回复风格精校准 — 变更方案设计

> 状态：待实施
> 日期：2026-05-18
> 基于 profile-a（林巅峰）的回复样例

---

## 1. 背景

首页晨报（Morning Brief）是用户打开 App 后看到的第一条 AI 回复，当前回复风格为"书面正式、单段、隐藏数值"。需要将其转变为"温暖有个性、多段结构、数据透明、含交互选项"的风格，以提升用户黏性和信任感。

### 1.1 当前回复特征

- 单段纯文本，80-200 字
- 语气书面正式（"极佳恢复状态"、"疲劳累积"）
- HRV/血氧/静息心率禁止输出具体数值（interpretation-only）
- 无交互元素，纯被动展示
- microTips 作为独立字段输出

### 1.2 目标回复特征

- 最终首页卡片由 `summary` 叙事正文 + `actions` 结构化选项共同组成，整体阅读量约 300-500 字
- `summary` 负责开场、交叉分析、建议理由和选择引导，建议 220-420 字，不在正文内重复完整选项列表
- 语气温暖、口语化、第一人称，像朋友在耳边提醒
- 所有指标可引用具体数值，用生活化比喻包装
- 每次回复附带 2-3 个交互选项（actions）
- microTips 融入 summary 主文本，不再作为独立字段

## 2. 回复样例对照

### 2.1 进餐事件

**当前回复：**

> 您刚刚完成了午餐，结合昨晚充足的高质量睡眠，身体目前处于极佳恢复状态。虽近期压力负荷较低，但 HRV 指标呈下降趋势，提示需关注潜在疲劳累积。建议午后进行适度户外活动以激活代谢，补齐今日暂时的运动缺口。本周整体走势稳健，请继续保持高质量作息。

**期望回复：**

> 巅峰，吃得不错！检测到你的心率正在随代谢平稳回升。
>
> 虽然你昨晚睡了快 8 小时，但这几天的 HRV 正在悄悄"阴跌"（从 110ms 降到了 95ms），这通常是身体在提醒我：你最近的"高压电池"还没充饱。
>
> 现在的建议：与其下午在办公室坐着消耗掉刚摄入的能量，不如现在去外面走 15 分钟？
>
> 理由：阳光和低强度步行能帮你拉平血糖曲线，同时给你的副交感神经换个气，阻止 HRV 继续下滑。
>
> 今日目标：你还有 4000 步的缺口，走完这趟我们就离目标不远了。
>
> 你需要我帮你：
>
> 🕒 开启 15 分钟"餐后漫步"模式？（我会实时监控你的代谢效率）
>
> 🔕 开启 20 分钟"深度充电"（冥想/午休）？（如果感觉脑力疲劳，这个对 HRV 更有好处）
>
> 请选择 1 或 2，或者直接出发，我会静默记录。

### 2.2 有氧运动事件

**当前回复：**

> 刚刚监测到你在用餐后随即开始了运动，这可能会给消化系统带来负担。昨晚十小时的高质量睡眠为你提供了极佳的恢复基础，深睡与快速眼动时长均很理想。虽然心率变异性近期呈现下降趋势，提示身体处于抗压阶段，但充足的休息能有效缓解疲劳。建议立即降低当前的运动强度，避免剧烈跳跃，并在接下来两小时内密切观察腹部反应。本周趋势整体平稳，需注意训练与饮食的间隔。

**期望回复：**

> 巅峰，先慢下来！监测到你刚吃完饭就开始了高强度有氧。
>
> 虽然你昨晚睡得像个职业运动员（深睡很足），但你的 HRV 已经在压力边缘徘徊了。现在剧烈运动，你的胃部供血会被肌肉"抢走"，不仅消化受阻，还会加剧你的系统性疲劳。

> 我的建议：把现在的"跑步"降档为"慢走"。把高强度训练往后挪 90 分钟，那时候你的血糖最稳定，爆发力也更好。
>
> 你想怎么做？
>
> 🚶 切换为"餐后消食"模式（我会重新设定心率预警区间，保护你的胃）。
>
> ⏯️ 暂停运动计时（90 分钟后我再提醒你开始正式训练）。
>
> 🏃 坚持继续（如果你一定要练，我会全程严密监控你的心率恢复斜率）。

> 请点击选项，或者直接慢下脚步，我能感觉到你的节奏变化。

### 2.3 摄入咖啡事件

**当前回复：**

> 今晨检测到可能的酒精摄入迹象，紧接着的有氧运动使心率出现波动。结合近期HRV下降的趋势，提示自主神经系统承受了一定压力。尽管睡眠时长达标，但心脏负荷因可能的物质摄入而有所上升。下午疑似摄入的咖啡因虽能提神，但建议避免高强度训练，改为温和的拉伸或冥想，整体状态需在本周加强监测与恢复。

**期望回复：**

> 巅峰，这杯咖啡来得正是时候，看来下午的疲劳感确实有点重。
>
> 但有个"生物学提醒"：根据你个人的代谢斜率，这杯咖啡因在你体内的半衰期约为 6 小时。这意味着今晚 11 点你躺下时，血液里还有一半的咖啡因在活跃。

> 今晚的风险：虽然它能让你现在精神百倍，但可能会偷走你今晚 30% 的深度睡眠时长。鉴于你本周 HRV 已经在走下坡路了，我们得做个平衡。

> 我为你准备了两个"抵消"方案：
>
> 🧊 深度冷启动（推荐）：晚饭后洗个冷水澡或调低卧室温度 2℃。这能物理诱导核心体温下降，对冲咖啡因带来的神经兴奋。
>
> 🧘 晚间"强制静息"：21:00 后我会为你开启"无干扰模式"，并引导你做一组 5 分钟的呼吸训练，强行拉回你的副交感神经。
>
> 你想尝试哪种方式来保住今晚的睡眠？
>
> [ A. 方案 1：物理降温 ]
>
> [ B. 方案 2：神经静息 ]
>
> [ C. 没关系，我今晚打算熬夜 ]
>
> 选好后，我会调整今晚的监测逻辑，并在 21:00 准时提醒你。

## 3. 模式分析

### 3.1 最终卡片结构模式

| 段落 | 占比 | 内容 | 来源样例验证 |
|------|------|------|-------------|
| ① 开场白 | ~10% | 用户姓名 + 逗号 + 事件相关即时观察 | 4/4 一致 |
| ② 交叉分析 | ~35% | 最近事件 × 24h 恢复状态 × 7d 趋势，引用具体数据 + 比喻 | 4/4 一致 |
| ③ 结构化建议 | ~35% | 具体行动 + 理由 + 时间 + 目标关联 | 4/4 一致 |
| ④ 选择引导 | ~10% | 用一句自然问句把用户带到选项区域 | 4/4 一致 |
| ⑤ `actions` | ~10% | 2-3 个行动方案，emoji + 标题 + 描述 + 已实现的 AI 后续动作 | 4/4 一致 |

> 注：当前 system 的 60/30/10 比例（recentEvents/24h/trend7d）被新的表达顺序替代。周趋势不再是独立段落，而是融入交叉分析中。样例里选项看起来在正文内，但工程实现应以结构化 `actions` 字段承载选项，前端组合渲染后形成同样的阅读体验，避免 `summary` 和按钮区域重复展示。

### 3.1.1 样例背后的表达语法

四个样例不是四套硬编码模板，而是同一种表达语法在不同事件上的展开：

1. **事件钩子**：先抓住用户刚发生的事，给出一句即时反馈。语气随事件风险变化：正向事件先肯定，风险事件先提醒。
2. **身体张力**：把当前事件和恢复背景放在一起形成“为什么现在要注意”的张力，例如吃饭 × HRV 下滑、咖啡因 × 晚间深睡风险、专注 × 脑力疲劳。
3. **机制解释**：用 1 个生理机制解释建议，不堆术语；术语出现时必须有生活化翻译。
4. **具体行动**：建议必须可立即执行，包含动作、时长或时间点，并说明做了之后保护什么指标或目标。
5. **协作姿态**：结尾不是命令用户，而是问“你想怎么做”，并给出 AI 可以配合的选项。

这套语法必须能泛化到未出现在样例里的事件，例如低睡眠、压力高、活动不足、血氧异常、数据缺失、timeline pending 等场景。

### 3.2 开场白模式

格式：`{用户姓名}，{事件钩子}！{即时观察}`

| 事件类型 | 开场白 |
|----------|--------|
| 进餐 | 巅峰，吃得不错！检测到你的心率正在随代谢平稳回升。 |
| 有氧运动 | 巅峰，先慢下来！监测到你刚吃完饭就开始了高强度有氧。 |
| 摄入咖啡 | 巅峰，这杯咖啡来得正是时候，看来下午的疲劳感确实有点重。 |
| 专注 | 巅峰，检测到你已经深度专注 90 分钟了。你的脑力电池正在高速放电。 |

**设计要点：**
- `{用户姓名}` 来自 `context.profile.name`，不是固定品牌名
- 开场白语气与事件性质匹配：正面事件用肯定语气（"吃得不错"），风险事件用提醒语气（"先慢下来"）
- 即时观察紧跟开场，给出实时反馈

### 3.3 数据引用模式

**原则性放开**：所有可用且与建议有关的指标均可引用具体数值，但必须用比喻、机制解释或行动含义包装。

| 指标 | 旧规则 | 新规则 | 样例 |
|------|--------|--------|------|
| HRV | 禁止输出数值 | 可引用趋势变化方向和幅度 | "从 110ms 降到了 95ms"、"在压力边缘徘徊"、"走下坡路"、"进一步崩盘" |
| 睡眠 | 可引用时长 | 保持不变 | "睡了快 8 小时"、"深睡很足" |
| 血氧 | 禁止输出数值 | 可引用百分比 | — |
| 静息心率 | 禁止输出数值 | 可引用 bpm | — |
| 步数/活动 | 可引用 | 保持不变 | "还有 4000 步的缺口" |
| 时间/时长 | 可引用 | 保持不变 | "专注 90 分钟"、"半衰期约 6 小时" |

**核心原则**：
- 每个数值必须服务于一个判断或行动，禁止纯数据罗列
- 只能引用输入上下文中存在、或代码明确计算并传入 prompt 的数值
- 不允许为了贴近样例编造“30% 深睡损失”“6 小时半衰期”“4000 步缺口”等数字；如果是估算，必须由上游算法显式提供并标注为估算
- 缺失数据必须明确说数据暂不可用，不能用 profile baseline、常识阈值或语气包装补出一个看似真实的值
- baseline 可以作为相对比较依据，但不要在文案里机械输出“baseline/参考值/正常范围”等分析术语

### 3.4 比喻风格

| 专业概念 | 比喻表达 |
|----------|----------|
| HRV 下降 | "阴跌"、"走下坡路"、"崩盘"、"在压力边缘徘徊" |
| 恢复能力 | "高压电池还没充饱"、"脑力电池正在高速放电" |
| 消化影响 | "胃部供血被肌肉'抢走'" |
| 咖啡因影响 | "偷走你今晚 30% 的深度睡眠" |
| 副交感神经 | "给你的副交感神经换个气"、"强行拉回副交感神经" |
| 血糖管理 | "拉平血糖曲线" |

### 3.5 交互选项模式

**每次必有**，格式统一：

```
{emoji} {标题}（{简短描述}）
```

| 事件 | 选项数 | 选项内容 |
|------|--------|---------|
| 进餐 | 2 | 🕒 餐后漫步 / 🔕 深度充电 |
| 有氧 | 3 | 🚶 餐后消食 / ⏯️ 暂停计时 / 🏃 坚持继续 |
| 咖啡 | 3 | 🧊 深度冷启动 / 🧘 晚间静息 / 熬夜 |
| 专注 | 3 | 🧘 脑力重置 / ⏳ 再给15分钟 / 🔇 静默模式 |

**每个选项包含**：
- `id`：唯一标识（如 "opt-1"）
- `emoji`：单个 emoji
- `title`：行动标题（4-8 字）
- `description`：简短描述行动内容
- `aiPromise`：选择后 AI 会做什么，必须匹配当前已实现能力

**工程约束**：
- `summary` 只写“你想怎么做？”这类选择引导，不内嵌完整选项列表
- `actions` 是唯一的选项数据源，前端负责渲染按钮
- 如果当前版本只实现本地选中状态或记录行为，`aiPromise` 不能承诺“调整监测逻辑”“实时监控”等尚未接入的能力
- 若希望保留样例中的强承诺文案，执行计划必须同时实现对应 action handler，例如写入 session memory、触发 advisor chat、设置提醒或切换监测模式

### 3.6 语气特征

| 维度 | 旧 | 新 |
|------|-----|-----|
| 人称 | 第三人称/无主语 | 第一人称"我"，称呼"你" |
| 语气 | 书面正式 | 口语化、温暖 |
| 建议 | "建议适度运动" | "去外面走 15 分钟" |
| 理由 | 无或泛泛 | 每个建议都有"为什么" |
| 结尾 | "本周走势稳健" | "请选择..."、"我会静默记录" |

## 4. 架构决策记录

### 4.1 交互选项归属

**决策**：actions 作为首页卡片的一部分，新增 `ActionOptions` 组件直接在 `MorningBriefCard` 内渲染；`summary` 只负责叙事和选择引导，不重复渲染选项正文。

**原因**：
- 用户不希望跳转到其他页面才能交互
- 首页是最高频的触达点，交互选项在此能最大化用户参与
- 首页卡片已有按钮类 UI 基础（手动刷新按钮）

**影响**：
- `AgentResponseEnvelope` 新增 `actions?: ActionOption[]` 字段，homepage LLM 输出要求 2-3 个，fallback/旧数据允许为空
- 前端新增 `ActionOptions` 组件
- `onSelect` 的行为必须在文档和文案中保持一致：如果只做本地选中反馈，文案只能承诺“我会记录你的选择”；如果文案承诺提醒、静默记录、调整监测逻辑，则必须实现相应 handler

### 4.2 数据透明化

**决策**：对 Homepage 解除 HRV/SpO2/静息心率的 blanket masking，但改为“有依据、有用途、可解释”的数值引用。

**原因**：
- 期望样例中明确引用了 HRV 具体值（"从 110ms 降到了 95ms"）
- 用户信任度来自数据透明，而非数据隐藏
- 比喻和解读比隐藏数值更能传递信息

**影响**：
- 移除 `HOMEPAGE_INTERPRETATION_ONLY_METRICS` 常量及其相关引用
- system-builder 中 Homepage 也传递 baseline 具体值，供相对判断使用
- context-packet-renderer 中 Homepage 可输出具体数值和趋势，但缺失指标仍必须保留 missing 标记
- prompt 明确禁止编造未传入的数值、比例、半衰期、目标缺口或提醒时间

**保留的安全约束**：
- 咖啡因/酒精事件仍使用概率性语言
- 禁止医学诊断
- 严重异常仍建议就医

### 4.3 microTips 处理

**决策**：`microTips` 从必填字段降为可选字段，建议内容融入 summary 主文本。

**原因**：
- 期望样例中没有独立的 microTips 概念
- 新回复结构中"建议段"已承载了 microTips 的功能
- 避免信息重复（summary 说一遍，microTips 又说一遍）

**影响**：
- `microTips` 类型改为 `string[] | undefined`
- 前端 `MorningBriefCard` 移除 microTips 展示区域
- eval scorer 中 `buildMatchText` 适配 microTips 可选
- fallback 配置中 microTips 保留但不作为必需

### 4.4 开场白中的用户姓名

**决策**：开场白使用 `context.profile.name`，以"打招呼"方式开始文案。

**原因**：
- "巅峰"是 profile-a 林巅峰的名字，不是品牌标识
- 使用用户姓名打招呼增加个性化体验
- Prompt 模板中通过变量引用实现，不硬编码

**实现方式**：
- system prompt 中已有 `## 用户信息` 段落传递 `name`
- template.md 中通过开场白规则引导 LLM 使用该姓名

### 4.5 summary 中的换行

**决策**：summary 字段支持换行（`\n`），前端使用 `whitespace-pre-line` 渲染；actions 独立渲染，不计入 summary 段落。

**原因**：
- 新回复结构包含多个叙事段落，需要换行分隔
- 不引入 markdown 渲染（过于复杂），用纯文本换行即可
- 前端 CSS `whitespace-pre-line` 原生支持

**影响**：
- `MorningBriefCard` 的 summary 渲染从 `<p>` 改为 `<div className="whitespace-pre-line">`，避免多段文本放在单个 `<p>` 中产生语义问题
- LLM 输出中使用 `\n` 分隔段落
